1. Introduction

This is less a manual than a shared notebook. We are filling it in together.

Two of us have already tried these tools on a Raspberry Pi 4B (4 GB). That work went well, and it left one question open: what happens on a Raspberry Pi 3 with 1 GB of RAM? Nobody has measured that yet. If you have that hardware, and the time and interest, you can answer it in a way we cannot.

How to read this guide

  • Everything below comes from real runs on a Pi 4B, unless a note says otherwise.
  • A tag reading Not yet tested on a Pi 3 marks advice that we have not verified on a Pi 3. Treat it as a starting point, and tell us where it is wrong.
  • Each technical section ends with a dashed box for your observations. Anything you see that differs from this text is valuable, including "it did not work".

You do not need to use GitHub. You can send your results and questions by email. We will add them to this page, with credit in whatever form you prefer (full name, handle, or no mention).

What this guide does not cover

  • Production operation. Backups and restores, log rotation, monitoring, upgrades and rollbacks, what happens when the SD card fails or the power is cut suddenly. This guide is an experiment, not a deployment manual.
  • Exposure to the Internet. We assume a trusted local network, or an SSH tunnel. We do not cover TLS, authentication in front of the map servers, or firewall design.
  • Our settings are for experiments. For example, the mapfile in section 4.3 enables every WMS request type, and the example user has passwordless sudo. Tighten such things before you leave a server running on its own.

Which one you need depends on what you want to do. If you only need to serve maps, MapServer is likely enough. If you need to edit features through the web (WFS-T), or manage permissions per layer, GeoServer offers those features and MapServer does not.

Before either, it is worth asking what you actually need. If the goal is only to publish maps, there are even lighter approaches (for example pre-built vector tiles served as static files, or small tile servers). GeoServer and MapServer are worth their cost when you want standard OGC services such as WMS and WFS, and, with GeoServer, editing.

Terms used in this guide

  • WMS: a standard way to request a map as an image. WFS: a standard way to request the features (points, lines, polygons and their attributes) themselves. WFS-T: WFS with editing.
  • GML: the default XML format for WFS answers. GeoJSON: a lighter alternative.
  • JVM and heap: the Java runtime, and the memory it may use for its objects.
  • systemd: the part of Ubuntu that starts and supervises services. CPU governor: the setting that decides how the CPU changes its speed.
  • CGI and FastCGI: two ways for a web server to run a program. Section 4.3 explains why the difference matters.
  • mapfile: MapServer's text file that describes a map (its data and styling).

What you need

  • A Raspberry Pi 3 (Model B or B+, 1 GB), a good SD card, and a power supply that keeps the board out of under-voltage.
  • A second computer for SSH, and a network connection.
  • Ubuntu Server 64-bit (24.04 LTS). We used the same OS on both Pi models so that OS differences would not confuse the comparison. Desktop editions are not suitable for 1 GB. Section 2 walks through installing it.

2. Prepare the Pi

Both servers in this guide start from the same place: a Pi 3 running Ubuntu Server, reachable over SSH. This section gets you there. If your board already runs Ubuntu Server 24.04 (64-bit) and you can log in, skip to section 3 or section 4, and just run the checks in 2.4.

2.1 Choose the operating system

We used Ubuntu Server 24.04 LTS, 64-bit (the "preinstalled server arm64+raspi" image). Ubuntu officially supports the Pi 3 and the Pi 4, so both boards can run the same OS, which keeps OS differences out of the comparison. Do not use a desktop edition: it does not fit in 1 GB.

Images are published at cdimage.ubuntu.com. The file we used on the Pi 4B was named ubuntu-24.04.5-preinstalled-server-arm64+raspi.img.xz. Pick the current 24.04 image with the same naming. Raspberry Pi Imager can also list it for you under Other general-purpose OS → Ubuntu. Imager may list a newer Ubuntu release first; choose 24.04 LTS explicitly, because all our measurements used it.

2.2 Write the SD card

Use Raspberry Pi Imager on your computer. Choose your Pi model, the Ubuntu Server image, and your SD card, then write it.

Writing an SD card erases the card you select. Check that the device shown is the SD card and not one of your computer's own disks.

Before the first boot you need to decide three things: a hostname, a user, and how you will log in. We recommend an SSH key and no password login. If you do not have a key yet, create one on your computer:

ssh-keygen -t ed25519
cat ~/.ssh/id_ed25519.pub     # this is the public key to give the Pi

There are two ways to give these settings to the Pi. Either is fine.

Not yet tested on a Pi 3

Route A: Imager's own settings dialog. When Raspberry Pi Imager offers "OS customisation" (the wording varies between versions), enter the hostname, user, SSH key, and Wi-Fi details there. This is the simplest route. We have not tested it on a Pi 3, so tell us how it goes. Two cautions:

  • Use the user name ubuntu. The service file in section 3.2 says User=ubuntu; if you choose another name, change it there too.
  • If you set up Wi-Fi this way, check that the cable port still gets an IP address. Our own tests showed that a Wi-Fi-only network file can leave the cable port without one (see the traps below). If that happens to you, please tell us.

Route B: a cloud-init file, which is what we used. Ubuntu reads two small text files from the SD card's boot partition (named system-boot) on its first start: user-data and network-config. Here is the user-data we used, with the values replaced by placeholders:

#cloud-config
hostname: YOUR-HOSTNAME
manage_etc_hosts: true

users:
  - name: ubuntu
    groups: [adm, sudo]
    shell: /bin/bash
    sudo: ["ALL=(ALL) NOPASSWD:ALL"]
    ssh_authorized_keys:
      - "ssh-ed25519 AAAA... your-public-key"

ssh_pwauth: false        # key-only login
disable_root: true

package_update: true
packages:
  - openjdk-17-jre-headless
  - curl
  - unzip
  - avahi-daemon         # makes YOUR-HOSTNAME.local resolve
  - tmux

And a network-config that covers both the cable and Wi-Fi (the Pi 3 has both). This is an example in the standard Ubuntu (netplan) format; replace the Wi-Fi name and password:

network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true
      optional: true
  wifis:
    wlan0:
      dhcp4: true
      optional: true
      access-points:
        "YOUR-WIFI-NAME":
          password: "YOUR-WIFI-PASSWORD"

The Wi-Fi password stays in this file, in plain text, on the SD card. Keep that in mind if you share the card or the file.

Traps we fell into while doing this. Each one cost us a re-flash or an hour:

  • Write both ethernets: and wifis:. The file replaces the default network setup as a whole. With only wifis:, the cable port gets no IP address: the link light comes on, but nothing is reachable.
  • Put dhcp4: true on wlan0. Without it, Wi-Fi connects to the access point and looks "up", yet the Pi never gets an IPv4 address.
  • Do not set renderer: NetworkManager. Ubuntu Server does not include it, and the whole Wi-Fi block is then silently ignored.
  • cloud-init runs only once per SD card. If you edit user-data or network-config after the first boot, nothing happens. Write the card again from scratch.
  • Package installation needs the network to be up at first boot. If the network was not working then, the packages: step fails silently and none are installed. Fix the network, then re-flash, or run sudo apt install by hand afterwards.
  • Check which key you gave it. If ssh says "Permission denied", first confirm that the public key in user-data is the one you are actually using. cloud-init installs whatever key you wrote, even a wrong one, which looks exactly like "cloud-init did not run".
  • Ubuntu Server has no avahi-daemon by default. Without it, YOUR-HOSTNAME.local never resolves. Install it (as above), or find the Pi's IP address in your router.

One more thing, which we ran into with Imager's command-line mode, and which may apply to other versions: it did not always copy the cloud-init files onto the card as requested (see rpi-imager issue 1385). Our workaround was to mount the card's system-boot partition after writing, and copy the two files in by hand before inserting the card into the Pi. If you use Route B, check that the files are really there.

2.3 First boot and login

  1. Put the card in the Pi, connect the cable (or have your Wi-Fi ready), and power on.
  2. Be patient, and do not cut the power. On the first boot, Ubuntu expands the file system, installs the packages, and may run updates. A Pi 3 is slow at this. We have not timed it on a Pi 3, but expect it to take longer than on a Pi 4, possibly ten minutes or more.
  3. From your computer: 
    ssh ubuntu@YOUR-HOSTNAME.local
    or use the IP address if the name does not resolve.
  4. Once in, make sure the first-boot set-up has finished: 
    cloud-init status --wait
    If something looks wrong, cloud-init status --long and the file /var/log/cloud-init-output.log show what happened.

Right after the first boot, background updates may hold the package manager for a while. If sudo apt install fails with "Could not get lock", wait a few minutes and run it again.

If you re-write the same board with a new card image, the Pi will have a new SSH identity, and your computer will refuse to connect with a loud "REMOTE HOST IDENTIFICATION HAS CHANGED" warning. That is expected. Run ssh-keygen -R YOUR-HOSTNAME.local and connect again.

2.4 Check what you have

Run these and keep the output. The memory figure in particular is the baseline for everything that follows.

uname -m                           # expect: aarch64
grep Model /proc/cpuinfo           # expect: Raspberry Pi 3 Model B (or B+)
free -h                            # note "total", "used" and "available"
java -version                      # expect: OpenJDK 17
java -XX:+PrintCommandLineFlags -version   # shows which garbage collector Java chose
journalctl -k | grep -i voltage    # no output is good; "Under-voltage detected" is not

For reference, a freshly booted Ubuntu Server 24.04 on our Pi 4B used about 346 MiB with no swap. We do not yet know the figure for a Pi 3. On a 1 GB board it decides how much room is left for a server. The "total" shown by free may be somewhat below 1 GB, because part of the memory is reserved for the hardware.

Keep the board and the card healthy. A weak power supply causes strange, random failures on a Pi; if the system misbehaves, check power first (the command above shows under-voltage warnings). A good-quality SD card matters as much, especially for anything that writes a lot. A Pi 3 has no fan, and a small heatsink is a cheap precaution before you run long tests.

3. GeoServer setup

Reference setup on the Pi 4B: Ubuntu Server 24.04, GeoServer 3.0.1 (the bundled-Jetty binary, running as a systemd service), PostGIS for editable layers, and a public health-facilities point dataset of 8,975 features. This section explains that setup and marks where a Pi 3 will need different choices.

Shortest path to one image: install Java and unpack GeoServer (3.1), start it as a service and see it answer (3.2), publish the test points (5.1), then request one WMS image (5.1, last step). If you can see the dots, the installation works, and you can move on to benchmarking.

3.1 Install Java and GeoServer

We ran GeoServer on OpenJDK 17.

sudo apt update
sudo apt install -y openjdk-17-jre-headless unzip curl

For the reference track, use GeoServer 3.0.1. The “Platform Independent Binary” (the -bin.zip, which bundles Jetty) is about 127 MB. This link worked on 2026-10-01, from a container:

export GEOSERVER_VERSION=3.0.1
curl -fL -o geoserver-${GEOSERVER_VERSION}-bin.zip \
  "https://sourceforge.net/projects/geoserver/files/GeoServer/${GEOSERVER_VERSION}/geoserver-${GEOSERVER_VERSION}-bin.zip/download"
sudo mkdir -p /opt/geoserver
sudo unzip -q geoserver-${GEOSERVER_VERSION}-bin.zip -d /opt/geoserver
sudo mkdir -p /opt/geoserver/data_dir
sudo chown -R "$USER:$USER" /opt/geoserver/data_dir

For the exploration track, look up the current release at geoserver.org/release/stable/, set GEOSERVER_VERSION to it, and use the download link from that page. The download takes a while on a slow connection.

Checked in a container The archive unpacks flat: there is no version-numbered folder, so start.jar lands directly in /opt/geoserver. (The archive contains its own data_dir folder, so the mkdir above changes nothing, and is harmless.) Confirm it:

find /opt/geoserver -maxdepth 3 -name start.jar -print
# expect exactly one line: /opt/geoserver/start.jar

The program files stay owned by root. Only the data directory is writable by the service user.

Why not Docker? At the time of writing we found no official GeoServer image for arm64 (the 64-bit ARM architecture of the Pi 3 and 4), and third-party images that claim arm64 support were reported to fail on real hardware. Running the binary directly also saves memory, which matters on 1 GB.

Docker is still possible: our colleague ran GeoServer 2.28.4 in an official multi-arch Tomcat 9 image with GeoServer's .war file. We chose the bundled-Jetty binary for the memory reason above, not because Docker cannot work.

3.2 Run it as a service, with a memory limit

This is the systemd unit we used on the Pi 4B. The heap sizes in JAVA_OPTS are the ones to change for the Pi 3. If your user name is not ubuntu, change User= as well.

# /etc/systemd/system/geoserver.service
[Unit]
Description=GeoServer (Jetty-bundled binary)
After=network.target

[Service]
Type=simple
User=ubuntu
Environment=GEOSERVER_HOME=/opt/geoserver
Environment=GEOSERVER_DATA_DIR=/opt/geoserver/data_dir
Environment="JAVA_OPTS=-Xms256m -Xmx512m -Djetty.http.host=127.0.0.1"
WorkingDirectory=/opt/geoserver
ExecStart=/usr/bin/java $JAVA_OPTS -DGEOSERVER_DATA_DIR=${GEOSERVER_DATA_DIR} -jar /opt/geoserver/start.jar
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now geoserver.service
journalctl -u geoserver.service -f

Starting takes a while on a small board (about 8 seconds in our container, which is much faster than a Pi will be). Check that the service is running, and that it answers:

systemctl status geoserver.service --no-pager     # expect: active (running)
curl -I http://localhost:8080/geoserver/web/      # expect: HTTP/1.1 302 Found
sudo ss -tlnp | grep 8080                         # expect: 127.0.0.1:8080 and nothing else

A "302 Found" is correct: GeoServer redirects you to its login page. "Connection refused" means it is not up yet (or it stopped; look at journalctl -u geoserver.service).

Two details that cost us time:

  • Environment="JAVA_OPTS=..." must be quoted. Unquoted, systemd treats everything after the first space as a separate, invalid assignment and silently drops it.
  • Inside the ExecStart line, write ${GEOSERVER_DATA_DIR} with braces. Without them the variable is not expanded, and GeoServer logs a misleading error on every request.

3.3 Keep the admin interface private, and change the password

The unit above binds Jetty to 127.0.0.1 only, so GeoServer is not reachable from the network. Reach the admin page through an SSH tunnel from your other computer:

ssh -L 8080:localhost:8080 ubuntu@<your-pi>
# then open http://localhost:8080/geoserver/web/ on your computer

Before anything else, change the default admin password (the default is admin / geoserver). Do this before exposing the server in any way.

3.4 Adjustments for 1 GB

Not yet tested on a Pi 3

The reference setup used -Xms512m -Xmx2048m on the 4 GB board. We reduced the heap to -Xms256m -Xmx512m on that same board, as a rehearsal for the 1 GB board (the unit file above uses these smaller values). What we saw:

  • With sustained load, the smaller heap was only about 10% slower for a heavy request.
  • On the first request after starting GeoServer with the small heap, we saw stalls of 12 to 30 seconds or more. (30 seconds was our test client's time limit, so the real delay may have been longer.) In our tests this happened after every JVM start, for the first request that produced GML (WFS's default XML format), even a small one. GeoJSON output and WMS did not show it. (In our container check, on a fast machine, the first GML request took about 1.1 seconds and the second about 0.05 seconds: the same one-time cost, but much smaller. How large it is depends on how fast the CPU is.) It was not garbage collection. The cost appears to be first-time class loading and reflection set-up.
  • Practical advice: after a restart, send one throwaway GetFeature request and wait for it, before you begin any timing.

Things we have not measured, and that are worth your attention:

  • Total memory. The JVM's real memory use is larger than -Xmx. On the 4 GB board with a 2 GB heap cap, the process sat near 1 GB. Whether a 512 MB heap plus the operating system fits comfortably in 1 GB is the central question. Watch free -h and systemctl show geoserver.service -p MemoryCurrent. If the process disappears, check whether the kernel stopped it for lack of memory: journalctl -k | grep -i "out of memory".
  • A rough memory budget. In our 1 GB container, GeoServer with -Xms256m -Xmx512m and this small test layer used about 425 to 436 MB of resident memory right after it started, and about 515 to 518 MB after the benchmark. It was not killed. If a Pi 3's Ubuntu uses about as much as our Pi 4B did (346 MiB), then 346 + 515 is about 860 MiB, which is almost everything a 1 GB board shows as available. That leaves very little room, and larger data will need more. This is arithmetic from two different machines, not a Pi 3 measurement.
  • A different garbage collector. Java chooses its default collector by machine size. On a machine as small as a Pi 3 it may pick a simpler one than the one in our Pi 4B logs. That would change behaviour and timings. Record which one you got (see section 2.4).
  • A hint from a 1 GB limit on a bigger board. Our colleague ran GeoServer in a container capped at 1 GB on the Pi 4B. It used about 450 MB when idle and 450 to 570 MB under a four-worker load, and was never killed for running out of memory. The data was small (5,000 points), so this shows that GeoServer can start within 1 GB, not that it copes with heavy use.
  • Swap. Our Pi 4B ran with no swap. On a 1 GB board you may want some, but swap on an SD card is slow and wears the card. Compressed swap in memory (zram) avoids the wear, but we have not tried it.
  • PostGIS. It runs as a second service next to GeoServer and takes memory too. You may prefer to start with a read-only layer (see 3.5) before adding it.
  • Run one server at a time while you measure. GeoServer and MapServer together would compete for the same 1 GB, and the numbers would mean little.

3.5 Data: choose the storage format on purpose

BackendReadsConcurrent WFS-T writes (Pi 4B)
GeoPackageFineFailures grew with concurrency: 0% at 1 writer, 25% at 4, 45% at 8, 75% at 16
PostGISFine0 errors at every level tested, up to 16 writers

GeoPackage is a single SQLite file, and SQLite allows only one writer at a time, so this is a property of SQLite (as used by GeoServer for GeoPackage) and not of the Pi. For a read-only service, GeoPackage is the simpler choice. For editing by several people at once, use PostGIS. If you must use GeoPackage, keep to one writer.

3.6 Three cheap improvements

These were measured on the Pi 4B. Try them on the Pi 3 and tell us whether the effect is the same.

  1. Ask for GeoJSON instead of GML when you request many features. Add outputFormat=application/json to a WFS GetFeature request. A full dump of 8,975 features was 2.3 to 2.5 times faster, with zero errors either way. The default GML output is the main cost.
  2. Set the CPU governor to performance. On our Pi 4B, the default was ondemand. Switching raised WMS map-rendering throughput by 30 to 50%. 
    for g in /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor; do
  echo performance | sudo tee "$g"
done
    This resets on reboot. To make it permanent, put the same loop in a systemd oneshot unit that runs at boot (with RemainAfterExit=yes). Keep an eye on temperature (/sys/class/thermal/thermal_zone0/temp, in thousandths of a degree). Our Pi 4B stayed between 64 and 69 °C under light load. A Pi 3 without a heatsink may get hot sooner and slow itself down (throttling); we have not measured it.
  3. Do not bother with paging. Splitting a big dump into startIndex/count pages made sequential fetching about 1.9 times slower and did not help when done in parallel.

Also tried and not worth pursuing on our setup: class-data sharing (AppCDS) for the cold-start stall, the Marlin renderer, PostgreSQL shared_buffers/work_mem tuning, and the JAI/ImageIO native acceleration (no aarch64 build exists).

3.7 What the Pi 4B managed, for reference

  • WFS-T edits on PostGIS: zero failures in sequential and concurrent tests, including 1,200 insert-and-delete cycles over two hours.
  • Long run: a mixed read/write soak test of about 30 hours produced no server-side errors. Memory grew by about 130 MB, mostly early on, then levelled off. (Three read iterations failed, traced to the tester's own SSH tunnel dying, not to the Pi.)
  • The one workload that genuinely maxes it out: a single request for the entire unfiltered dataset. Throughput stayed near 0.7 requests per second no matter how many clients asked, because the work is limited by a single CPU core. Filtered requests, by contrast, ran at roughly 25 to 31 per second once several clients were asking (about 12 per second for a single client). If a client only needs a small area or a few attributes, ask for exactly that.

These numbers are from a Pi 4B with 4 GB and a 4-core CPU at higher clock speeds than a Pi 3. Do not expect to reproduce them; the comparison is what we are after.

4. MapServer setup

How much of this section has been run. Everything in 4.1 to 4.4 was run end to end on 2026-10-01 in an Ubuntu 24.04 arm64 container: install, configuration file, mapfile, plain CGI, FastCGI, and the benchmark script. It has not been run on a Pi, and never on a Pi 3. The mapfile and Apache settings are ours, written from the documentation, and are not our colleague's working files. Paths and settings may need adjusting on your board; please tell us what you had to change.

A colleague set up MapServer on a Pi 4B (4 GB) of the same kind, in a container based on Debian trixie-slim, with Apache 2, mod_fcgid, and the distribution's own MapServer packages (version 8.4.0). No source build was needed. On Ubuntu Server 24.04 the same package names work and give MapServer 8.0.1 (we checked), so you can install them directly on a Pi 3.

4.1 Install

sudo apt install -y apache2 libapache2-mod-fcgid cgi-mapserver mapserver-bin
sudo a2enmod fcgid

Checked in a container On Ubuntu 24.04 this installs MapServer 8.0.1 and Apache 2.4.58. The program is /usr/bin/mapserv, and it is also reachable as /usr/lib/cgi-bin/mapserv (a link to it). Check what you got, including FastCGI support, which the later steps need:

mapserv -v | cut -d' ' -f1-3                       # expect: MapServer version 8.0.1
mapserv -v | tr ' ' '\n' | grep -E 'FASTCGI|WMS_SERVER'
# expect two lines: SUPPORTS=WMS_SERVER and SUPPORTS=FASTCGI
apache2ctl configtest                             # expect: Syntax OK

(configtest may also warn that it cannot determine the server's fully qualified domain name. That is harmless here.)

Not yet tested on a Pi 3

MapServer's small footprint is the reason to try it on a Pi 3. In our container check, one FastCGI process held about 44 MB of resident memory. We have not measured the whole Apache and MapServer combination on a Pi.

4.2 The step everyone misses: MapServer 8 needs a configuration file

Since MapServer 8, a global configuration file is mandatory. It contains MS_MAP_PATTERN: a pattern saying which mapfile paths may be loaded through the map= URL parameter. When MapServer cannot find a configuration file at all, every request fails with:

msLoadConfig(): Unable to access file.

The message does not say which file it wanted. Checked in a container Here is what we observed on Ubuntu 24.04 (MapServer 8.0.1):

SituationResult
No configuration file anywheremsLoadConfig(): Unable to access file.
File at /etc/mapserver.conf, nothing else setWorks
File somewhere else, MAPSERVER_CONFIG_FILE not set (a web server does not pass your shell's variables)msLoadConfig(): Unable to access file.
File somewhere else, MAPSERVER_CONFIG_FILE pointing to itWorks
File found, but the map path does not match MS_MAP_PATTERNmsCGILoadMap(): Web application error. CGI variable "map" fails to validate.

So, on Ubuntu, the simplest fix is to put the file at /etc/mapserver.conf. Only if you keep it elsewhere do you have to pass MAPSERVER_CONFIG_FILE to the MapServer process. Our colleague's container (Debian trixie, MapServer 8.4.0) needed the variable passed explicitly, so the default location may differ between builds. If you see the error, check these in order: does the file exist, can the web server's user read it, and does the variable (if you need it) reach the process.

This is the file we used. The pattern must match the folder and file names of your mapfiles:

# /etc/mapserver.conf
CONFIG
  ENV
    MS_MAP_PATTERN "^/srv/mapfiles/[A-Za-z0-9_]+\.map$"
  END
END

Step 1: test MapServer on its own, without Apache. This separates a configuration problem from a web-server problem:

MAPSERVER_CONFIG_FILE=/etc/mapserver.conf /usr/lib/cgi-bin/mapserv -nh \
  "QUERY_STRING=map=/srv/mapfiles/demo.map&SERVICE=WMS&REQUEST=GetCapabilities" | head -20

Expect the start of an XML document (<WMS_Capabilities ...) that names your layer (<Name>points</Name> appears further down), not an error message. If you see msLoadConfig() here, the problem is the configuration file (4.2), and Apache is not involved yet.

Step 2: let Apache run it as plain CGI. Create /etc/apache2/conf-available/mapserver.conf containing one line, then switch it on. (With the file at /etc/mapserver.conf the line is not strictly needed, but it is harmless, and it is required if you keep the file elsewhere.)

SetEnv MAPSERVER_CONFIG_FILE /etc/mapserver.conf
sudo a2enmod cgid
sudo a2enconf mapserver
sudo apache2ctl configtest          # expect: Syntax OK
sudo systemctl reload apache2
apache2ctl -M | grep -E 'cgi|fcgid' # expect: cgid_module and fcgid_module

(On Ubuntu the folder /usr/lib/cgi-bin is already served at /cgi-bin/: the serve-cgi-bin setting is on by default.)

Step 3: request a real map. This is the URL to give to the benchmark script in 5.3:

http://localhost/cgi-bin/mapserv?map=/srv/mapfiles/demo.map&SERVICE=WMS&VERSION=1.1.1&REQUEST=GetMap&LAYERS=points&STYLES=&SRS=EPSG:4326&BBOX=-10,-10,10,10&WIDTH=768&HEIGHT=768&FORMAT=image/png

Open it in a browser, or fetch it with curl -s -o test.png -w "%{http_code} %{content_type} %{size_download}\n" "URL" and then file test.png. Expect 200 image/png, a size of roughly 250 KB, and "PNG image data, 768 x 768". The picture is a field of red dots. If you get text instead of an image, read it: MapServer explains most mapfile mistakes in plain words.

4.4 CGI or FastCGI? Try both

Under plain CGI, the web server starts a new MapServer process for every request. Under FastCGI, a pool of MapServer processes stays alive and is reused. Which one is faster depends on how costly it is to start a process on your hardware:

Where (WMS GetMap)Plain CGIFastCGIGeoServer
Our colleague, Pi 4B5.1 to 5.5 req/s16.9 to 22.5 req/s (three runs)7.6 to 13.6 req/s (13.1 to 13.6 in the repeat runs)
Our container check, desktop-class machine68 to 76 req/s50 to 52 req/s62 to 124 req/s (varied from run to run)

On the Pi 4B, FastCGI won clearly. On the fast machine, plain CGI won on throughput, presumably because starting a process is cheap there. The two environments cannot be compared with each other.

There is a detail that throughput alone hides. In our container, FastCGI's median response time was about half that of plain CGI (26 ms against 54 ms), but in every FastCGI run one request took about 1.06 seconds, and that one slow request pulled the throughput down. We did not find out why (it may be how mod_fcgid starts and reuses its processes). This is one reason section 5.6 asks you to record the slowest request and not only the average speed.

A Pi 3 is slower than a Pi 4B, so we expect FastCGI to help, but that is a guess. It is exactly the kind of thing your measurement can settle.

The lesson: choosing how to deploy a server can matter as much as choosing which server to run. Do not judge MapServer, in either direction, before you have tried both modes on your own board.

Checked in a container With Apache and mod_fcgid, FastCGI means the URL points at the FastCGI form of the program. First check that your build supports it (section 4.1 shows how: look for SUPPORTS=FASTCGI). Then:

# /etc/apache2/conf-available/mapserver-fcgi.conf   (worked in our container check)
<Directory /usr/lib/cgi-bin>
  Options +ExecCGI
  AddHandler fcgid-script .fcgi
</Directory>
FcgidInitialEnv MAPSERVER_CONFIG_FILE /etc/mapserver.conf
FcgidMaxProcessesPerClass 4
sudo ln -s /usr/lib/cgi-bin/mapserv /usr/lib/cgi-bin/mapserv.fcgi
sudo a2enconf mapserver-fcgi
sudo apache2ctl configtest          # expect: Syntax OK
sudo systemctl reload apache2

Then use the same test URL as in 4.3, with mapserv.fcgi in place of mapserv, and expect the same kind of answer: 200 image/png, about 250 KB. After some load, look at the worker processes:

ps -eo pid,rss,args | grep mapserv.fcgi | grep -v grep
# rss is resident memory in KB. In our container each process was about 44,000 (44 MB)

To compare fairly, run the benchmark once against each URL, with nothing else changed.

Limit the number of FastCGI processes on a 1 GB board. By the mod_fcgid documentation, the defaults allow up to 100 processes per program and 1,000 in total. At about 44 MB each, that could use up all the memory under load. The line FcgidMaxProcessesPerClass 4 above is a safer start. In our container check, 3 processes were alive after the benchmark. We have not tested this on a Pi 3, so watch free -h while you try.

5. Benchmark procedure

The point of a benchmark is to let you compare two servers, or two settings, fairly. Use the same data, the same request, and the same procedure every time.

What this benchmark compares. One shared operation, WMS GetMap, under a deliberately simple workload. It is not a verdict on the overall capability, security, administration cost, or suitability of either server: they offer different things (see section 1). And for a 1 GB field server, the more useful question may not be “which is faster?” but “which workloads stay usable and recoverable within 1 GB?”. That is why section 5.6 asks you to record more than speed.

5.1 Make test data, and publish it in GeoServer

What is verified here, and what is not. Checked in a container The data script, the conversion, the layer settings, and the final map request were run. For the layer we used GeoServer's REST interface instead of the menus, with the same settings (file:data/points.shp, workspace demo). The menu steps below are written from GeoServer's own documentation, have not been run, and the labels may differ a little between versions. Tell us where they differ.

Both servers need the same points. First install the GDAL tools, which include the conversion program ogr2ogr:

sudo apt install -y gdal-bin

Save this as make_points.py. It writes 5,000 random points (longitude and latitude between -10 and 10) and always gives the same points, so two people get identical data:

#!/usr/bin/env python3
"""Write 5,000 random points (lon/lat between -10 and 10) as GeoJSON."""
import json, random

random.seed(1)                      # same data every time
kinds = ["A", "B", "C", "D"]
features = []
for i in range(5000):
    lon = random.uniform(-10, 10)
    lat = random.uniform(-10, 10)
    features.append({
        "type": "Feature",
        "geometry": {"type": "Point", "coordinates": [round(lon, 5), round(lat, 5)]},
        "properties": {"id": i, "kind": random.choice(kinds), "name": f"point-{i}"},
    })

with open("points.geojson", "w") as f:
    json.dump({"type": "FeatureCollection", "features": features}, f)
print("wrote points.geojson with", len(features), "points")

Turn it into a Shapefile (the format we used for both servers), and put a copy where each server will read it:

python3 make_points.py
ogr2ogr -f "ESRI Shapefile" points.shp points.geojson
ogrinfo -so points.shp points | grep "Feature Count"     # expect: Feature Count: 5000

sudo mkdir -p /opt/geoserver/data_dir/data /srv/data
sudo cp points.shp points.shx points.dbf points.prj /opt/geoserver/data_dir/data/
sudo cp points.shp points.shx points.dbf points.prj /srv/data/

Now publish it in GeoServer (reach the admin page through the tunnel from section 3.3):

  1. Log in to the admin page.
  2. Data → Workspaces → Add new workspace. Name: demo. Namespace URI: http://example.org/demo (any address works; it is only a label). Submit.
  3. Data → Stores → Add new Store → Shapefile. Workspace: demo. Data Source Name: points. Shapefile location: file:data/points.shp (a path relative to GeoServer's data directory). Save.
  4. On the page that follows, click Publish next to points.
  5. On the Data tab, click Compute from data (native bounding box), then Compute from native bounds (lat/lon bounding box). If the coordinate system field is empty or says "unknown", type EPSG:4326. (In our REST check, GeoServer found EPSG:4326 and the bounding box by itself.) Save.
  6. Data → Layer Preview. Click OpenLayers next to demo:points. You should see a map of dots.

From now on, the layer name in requests is demo:points. MapServer gets the same data in section 4.3. The map request that the benchmark uses is in 5.3. A single request such as that one should return a PNG of 768 × 768 pixels (about 140 KB in our check) before you start timing anything.

5.2 The recipe

  1. Same data on both servers. We generated 5,000 random points as a Shapefile and registered the identical dataset in GeoServer and in MapServer (see 5.1 and 4.3). If you use your own data instead, make sure both servers serve the same layer.
  2. One request type. A WMS GetMap request, identical every time (same bounding box, size, and format).
  3. Similar drawing. The two servers do not draw identically. In our container check, the same request returned a picture of about 139 KB from GeoServer and about 250 KB from MapServer: the dots have different sizes, colours, and edge smoothing, so equal pixels do not mean equal work. Before you compare speeds, make the symbol size, colour, and image settings as alike as you can, and write down the response size (the script in 5.3 prints it).
  4. Warm up first. Send one or two requests and wait for them. The first request after starting a server is not representative (see the cold-start stall in section 3.4).
  5. Four parallel workers, 20 requests each, 80 in total.
  6. Measure the wall-clock time from when the workers start to when the last one finishes.
  7. Throughput = 80 ÷ wall-clock seconds.
  8. Repeat at least three times and report the range, not a single number. Run-to-run variation is large (in our container, GeoServer ranged from 62 to 124 requests per second on the same machine).

Why wall-clock time? Adding up each request's own duration overstates the total when requests overlap. Dividing the number of requests by the real elapsed time gives what a user would actually experience.

5.3 A small script

This needs only Python 3, which Ubuntu already includes. Save it as bench.py, and fill in your own URL. It counts a request as an error unless a real image comes back. This matters, because a map server often reports a problem as a text message with an ordinary "200 OK" status, and that would otherwise look like a very fast success. It also prints the median (p50), the 95th percentile (p95), and the slowest request, and the average size of the images.

#!/usr/bin/env python3
"""4 workers x 20 requests; prints wall-clock throughput and latency."""
import sys, time, urllib.request
from concurrent.futures import ThreadPoolExecutor

URL = sys.argv[1]          # the full GetMap URL, in quotes
WORKERS, PER_WORKER = 4, 20

def fetch():
    """One request. Returns (ok, seconds, bytes). ok is True only if an image came back."""
    t = time.monotonic()
    with urllib.request.urlopen(URL, timeout=60) as r:
        body = r.read()
        ok = r.headers.get_content_type().startswith("image/") and len(body) > 0
    return ok, time.monotonic() - t, len(body)

def worker(_):
    results = []
    for _ in range(PER_WORKER):
        try:
            results.append(fetch())
        except Exception:
            results.append((False, 0.0, 0))
    return results

# Warm-up, not timed.
try:
    ok, _, _ = fetch()
except Exception as e:
    sys.exit(f"warm-up request failed: {e}")
if not ok:
    sys.exit("warm-up did not return an image. Open the URL in a browser to read the message.")

t0 = time.monotonic()
with ThreadPoolExecutor(max_workers=WORKERS) as pool:
    results = [r for part in pool.map(worker, range(WORKERS)) for r in part]
wall = time.monotonic() - t0

total = len(results)
errors = sum(1 for ok, _, _ in results if not ok)
good = sorted(s for ok, s, _ in results if ok)
def pct(p):
    return good[min(len(good) - 1, int(p * len(good)))] * 1000 if good else float("nan")
size = sum(b for ok, _, b in results if ok) / max(1, len(good))
print(f"requests={total} errors={errors} wall_s={wall:.2f} throughput={total / wall:.1f} req/s")
print(f"latency_ms p50={pct(0.5):.0f} p95={pct(0.95):.0f} max={pct(1.0):.0f} avg_bytes={size:.0f}")

Example call for the layer made in 5.1 (adjust host, layer, and bounding box if you use your own data). The & characters need the quotes:

python3 bench.py "http://localhost:8080/geoserver/wms?service=WMS&version=1.1.1&request=GetMap&layers=demo:points&styles=&bbox=-10,-10,10,10&width=768&height=768&srs=EPSG:4326&format=image/png"

For MapServer, use the test URL from section 4.3. The output looks like this (the numbers are from our container and mean nothing for a Pi):

requests=80 errors=0 wall_s=1.09 throughput=73.4 req/s
latency_ms p50=51 p95=62 max=70 avg_bytes=250393

If errors is not 0, do not trust the throughput figure until you know why.

5.4 Run it from the right place

There are two different tests, and they answer different questions. Say which one you ran.

  • Local-client test: run the script on the Pi itself. This measures the whole one-board setup, as a single-computer field server would run it. The script then competes with the server for the same four cores and the same memory.
  • Remote-client test: run it from another computer. This removes the competition for the Pi's CPU, and includes the network. On a Pi 3 the wired network is limited (it runs over USB 2, and the Model B is 100 Mbit/s), so map images may be limited by the network rather than by the server. Wi-Fi is slower and less steady still.
  • If you use an SSH tunnel for a long run, remember that a laptop that goes to sleep will kill the tunnel. In our 30-hour run, this was the only failure.

5.5 Record the machine state alongside the numbers

free -h
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
awk '{ printf "%.1f C\n", $1/1000 }' /sys/class/thermal/thermal_zone0/temp
journalctl -k | grep -i voltage

A hot board slows itself down (thermal throttling), an under-voltage warning means the results are unreliable, and the governor changes results by tens of percent, so numbers without these are hard to interpret later.

6. Known pitfalls

Every item here cost somebody real time. Look through the list before you start.

Choosing and deploying

  • CGI versus FastCGI can change the result, and in which direction depends on the hardware. On our colleague's Pi 4B, MapServer under CGI lost to GeoServer and under FastCGI it won. On a fast desktop-class machine, plain CGI was faster than FastCGI. Try both on your own board before you judge MapServer (see 4.4).
  • Tomcat and GeoServer must be from the same servlet generation. If you deploy GeoServer as a .war in Tomcat, it has to match. The GeoServer 2.28.4 we tried is a javax.servlet build and needs Tomcat 9. It did not start on Tomcat 11, which is a jakarta.servlet release; the symptom was a NoClassDefFoundError. The reference setup our colleague began from was written for Tomcat 11, and newer GeoServer lines are expected to need the jakarta generation, so check the release notes of the version you download before you pick a Tomcat image. The bundled-Jetty binary in section 3 avoids the question.
  • Docker is not automatically the easy path on ARM. No official GeoServer arm64 image at the time of writing; the workable route is an official Tomcat image plus the .war (see 3.1).

Configuration traps

  • Getting the Pi onto the network in the first place has its own traps: both cable and Wi-Fi in network-config, dhcp4: true on Wi-Fi, and cloud-init running only once per card (see 2.2).
  • MapServer 8 needs a configuration file, or it refuses every request. The error message (msLoadConfig(): Unable to access file.) means that no configuration file was found. On Ubuntu, put it at /etc/mapserver.conf; if it is elsewhere, MAPSERVER_CONFIG_FILE has to reach the process. A path that does not match MS_MAP_PATTERN gives a different message (see 4.2).
  • systemd quoting: quote Environment="JAVA_OPTS=..." and use ${VAR} with braces inside ExecStart (see 3.2).
  • GeoServer's REST shortcut for registering a Shapefile (the external.shp form) returned an unexplained error for us. The longer, standard XML-POST way to create a datastore worked.
  • Change the default GeoServer admin password before doing anything else, and keep the admin interface off the open network (see 3.3).

Performance surprises

  • The first GML request after a restart can stall for 12 to 30 seconds or more on a small heap. Warm up before you measure (see 3.4).
  • Asking for the whole dataset at once is the expensive operation. Filter, or request a small area (see 3.7).
  • GeoJSON is much cheaper than GML for large results (see 3.6).
  • The CPU governor matters, and it resets on reboot (see 3.6).
  • Too many FastCGI processes can exhaust 1 GB. Set a low limit (see 4.4).

Data and concurrency

  • GeoPackage is unreliable under concurrent writes; PostGIS is not (see 3.5). This comes from SQLite, not from the Pi.
  • PostGIS accumulates dead rows between automatic cleanups when you edit and delete a lot. In our two-hour test it was about 14% of live rows, harmless on a small table. On a large table with heavy editing, watch disk space.

Measuring

  • Do not compare numbers from different hardware or different data and call it a verdict. Our Pi 4B figures and our colleague's container figures used different data and different setups. Compare only what you ran under the same conditions.
  • A benchmark can look fast because every request failed. Map servers often report errors as text with a "200 OK" status. The script in 5.3 counts only real images as successes.
  • Check a suspicious result in two ways before believing it. One of us briefly concluded that container memory limits were switched off, because we had looked in the wrong place for the setting (the older cgroup version instead of the current one). The limit was working all along.
  • The 1 GB experiment on a 4 GB board did not settle the question. Limiting a container to 1 GB on the Pi 4B did not squeeze GeoServer, because it never used more than about 600 MB with that small dataset. A real Pi 3, with larger data and more load, is the test that counts.
  • A long test from a sleeping laptop will be interrupted. Run long tests from a machine that stays awake.
