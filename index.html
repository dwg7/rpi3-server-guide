1. Introduction

This is not a set of instructions to follow blindly. It is a notebook that we are filling in together.

Two of us have already tried these tools on a Raspberry Pi 4B (4 GB). That work went well, and it left one question open: what happens on a Raspberry Pi 3 with 1 GB of RAM? Nobody has measured that yet. You have that hardware, so you are in the best position to answer it.

How to read this guide

  • Everything below comes from real runs on a Pi 4B, unless a note says otherwise.
  • A tag reading marks advice that we have not verified on a Pi 3. Treat it as a starting point, and tell us where it is wrong.
  • Each technical section ends with a dashed box for your observations. Anything you see that differs from this text is valuable, including "it did not work".

You do not need to use GitHub. You can send your results and questions by email. We will add them to this page, with credit in whatever form you prefer (full name, handle, or no mention).

The two servers, briefly

GeoServerMapServer
Written inJava (needs a JVM)C
Memory appetiteLarge: hundreds of MB even when idleSmall (reported to run in tens of MB; not measured by us)
StrengthsWFS-T (editing over the web), WMTS, per-layer permissions (and GeoFence for finer rules), REST config API, web admin GUIFast, light WMS/WFS; configured through text files (mapfiles)
Question for a Pi 3Does it fit in 1 GB at all?Does its light footprint pay off?

Which one you need depends on what you want to do. If you only need to serve maps, MapServer is likely enough. If you need to edit features through the web (WFS-T), or manage permissions per layer, GeoServer offers those features and MapServer does not.

Before either, it is worth asking what you actually need. If the goal is only to publish maps, there are even lighter approaches (for example pre-built vector tiles served as static files, or small tile servers). GeoServer and MapServer earn their weight when you want standard OGC services such as WMS and WFS, and, with GeoServer, editing.

What you need

  • A Raspberry Pi 3 (Model B or B+, 1 GB), a good SD card, and a power supply that keeps the board out of under-voltage.
  • A second computer for SSH, and a network connection.
  • Ubuntu Server 64-bit (24.04 LTS). We used the same OS on both Pi models so that OS effects would not muddy the comparison. Desktop editions are not suitable for 1 GB. Section 2 walks through installing it.

2. Prepare the Pi

Both servers in this guide start from the same place: a Pi 3 running Ubuntu Server, reachable over SSH. This section gets you there. If your board already runs Ubuntu Server 24.04 (64-bit) and you can log in, skip to section 3 or section 4, and just run the checks in 2.4.

2.1 Choose the operating system

We used Ubuntu Server 24.04 LTS, 64-bit (the "preinstalled server arm64+raspi" image). Ubuntu officially supports the Pi 3 and the Pi 4, so both boards can run the same OS, which keeps OS differences out of the comparison. Do not use a desktop edition: it does not fit in 1 GB.

Images are published at cdimage.ubuntu.com. The file we used on the Pi 4B was named ubuntu-24.04.5-preinstalled-server-arm64+raspi.img.xz. Pick the current 24.04 image with the same naming. Raspberry Pi Imager can also list it for you under Other general-purpose OS → Ubuntu.

2.2 Write the SD card

Use Raspberry Pi Imager on your computer. Choose your Pi model, the Ubuntu Server image, and your SD card, then write it.

Writing an SD card erases the card you select. Check that the device shown is the SD card and not one of your computer's own disks.

Before the first boot you need to decide three things: a hostname, a user, and how you will log in. We recommend an SSH key and no password login. If you do not have a key yet, create one on your computer:

ssh-keygen -t ed25519
cat ~/.ssh/id_ed25519.pub     # this is the public key to give the Pi

There are two ways to give these settings to the Pi. Either is fine.

Route A: Imager's own settings dialog. When Raspberry Pi Imager offers "OS customisation" (the wording varies between versions), enter the hostname, user, SSH key, and Wi-Fi details there. This is the simplest route. We have not tested it on a Pi 3, so tell us how it goes.

Route B: a cloud-init file, which is what we used. Ubuntu reads two small text files from the SD card's boot partition (named system-boot) on its first start: user-data and network-config. Here is the user-data we used, with the values replaced by placeholders:

#cloud-config
hostname: YOUR-HOSTNAME
manage_etc_hosts: true

users:
  - name: ubuntu
    groups: [adm, sudo]
    shell: /bin/bash
    sudo: ["ALL=(ALL) NOPASSWD:ALL"]
    ssh_authorized_keys:
      - "ssh-ed25519 AAAA... your-public-key"

ssh_pwauth: false        # key-only login
disable_root: true

package_update: true
packages:
  - openjdk-17-jre-headless
  - curl
  - unzip
  - avahi-daemon         # makes YOUR-HOSTNAME.local resolve
  - tmux

And a network-config that covers both the cable and Wi-Fi (the Pi 3 has both). This is an example in the standard Ubuntu (netplan) format; replace the Wi-Fi name and password:

network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true
      optional: true
  wifis:
    wlan0:
      dhcp4: true
      optional: true
      access-points:
        "YOUR-WIFI-NAME":
          password: "YOUR-WIFI-PASSWORD"

Traps we fell into while doing this. Each one cost us a re-flash or an hour:

  • Write both ethernets: and wifis:. The file replaces the default network setup as a whole. With only wifis:, the cable port gets no IP address: the link light comes on, but nothing is reachable.
  • Put dhcp4: true on wlan0. Without it, Wi-Fi connects to the access point and looks "up", yet the Pi never gets an IPv4 address.
  • Do not set renderer: NetworkManager. Ubuntu Server does not include it, and the whole Wi-Fi block is then silently ignored.
  • cloud-init runs only once per SD card. If you edit user-data or network-config after the first boot, nothing happens. Write the card again from scratch.
  • Package installation needs the network to be up at first boot. If the network was not working then, the packages: step fails silently and none are installed. Fix the network, then re-flash, or run sudo apt install by hand afterwards.
  • Check which key you gave it. If ssh says "Permission denied", first confirm that the public key in user-data is the one you are actually using. cloud-init installs whatever key you wrote, even a wrong one, which looks exactly like "cloud-init did not run".
  • Ubuntu Server has no avahi-daemon by default. Without it, YOUR-HOSTNAME.local never resolves. Install it (as above), or find the Pi's IP address in your router.

One more thing, which we ran into with Imager's command-line mode, and which may apply to other versions: it did not always copy the cloud-init files onto the card as requested (see rpi-imager issue 1385). Our workaround was to mount the card's system-boot partition after writing, and copy the two files in by hand before inserting the card into the Pi. If you use Route B, check that the files are really there.

2.3 First boot and login

  1. Put the card in the Pi, connect the cable (or have your Wi-Fi ready), and power on.
  2. Wait a few minutes. On the first boot, Ubuntu is expanding the file system and installing packages. A Pi 3 is slow at this.
  3. From your computer: 
    ssh ubuntu@YOUR-HOSTNAME.local
    or use the IP address if the name does not resolve.
  4. Once in, make sure the first-boot set-up has finished: 
    cloud-init status --wait

If you re-write the same board with a new card image, the Pi will have a new SSH identity, and your computer will refuse to connect with a loud "REMOTE HOST IDENTIFICATION HAS CHANGED" warning. That is expected. Run ssh-keygen -R YOUR-HOSTNAME.local and connect again.

2.4 Check what you have

Run these and keep the output. The memory figure in particular is the baseline for everything that follows.

uname -m                           # expect: aarch64
grep Model /proc/cpuinfo           # expect: Raspberry Pi 3 Model B (or B+)
free -h                            # note "used" and "available"
java -version                      # expect: OpenJDK 17

For reference, a freshly booted Ubuntu Server 24.04 on our Pi 4B used about 346 MiB with no swap. We do not yet know the figure for a Pi 3. On a 1 GB board it decides how much room is left for a server.

Remember to keep the board and the card healthy. A weak power supply causes strange, random failures on a Pi. If the system misbehaves, check power first. A good-quality SD card matters as much, especially for anything that writes a lot.

3. GeoServer setup

Reference setup on the Pi 4B: Ubuntu Server 24.04, GeoServer 3.0.1 (the bundled-Jetty binary, running as a systemd service), PostGIS for editable layers, and a public health-facilities point dataset of 8,975 features. This section explains that setup and marks where a Pi 3 will need different choices.

3.1 Install Java and GeoServer

We ran GeoServer on OpenJDK 17.

sudo apt update
sudo apt install -y openjdk-17-jre-headless unzip curl

Check the current stable release at geoserver.org/release/stable/ and download the Platform Independent Binary (the -bin.zip, which bundles Jetty). Then:

export GEOSERVER_VERSION=X.Y.Z        # the version you downloaded
sudo mkdir -p /opt/geoserver
sudo unzip -q geoserver-${GEOSERVER_VERSION}-bin.zip -d /opt/geoserver
sudo mkdir -p /opt/geoserver/data_dir
sudo chown -R "$USER:$USER" /opt/geoserver/data_dir

The program files stay owned by root. Only the data directory is writable by the service user.

Why not Docker? At the time of writing we found no official GeoServer image for arm64 (the 64-bit ARM architecture of the Pi 3 and 4), and third-party images that claim arm64 support were reported to fail on real hardware. Running the binary directly also saves memory, which matters on 1 GB.

Docker is still possible: our colleague ran GeoServer 2.28.4 in an official multi-arch Tomcat 9 image with GeoServer's .war file. We chose the bundled-Jetty binary for the memory reason above, not because Docker cannot work.

3.2 Run it as a service, with a memory limit

This is the systemd unit we used on the Pi 4B. The heap sizes in JAVA_OPTS are the ones to change for the Pi 3.

# /etc/systemd/system/geoserver.service
[Unit]
Description=GeoServer (Jetty-bundled binary)
After=network.target

[Service]
Type=simple
User=ubuntu
Environment=GEOSERVER_HOME=/opt/geoserver
Environment=GEOSERVER_DATA_DIR=/opt/geoserver/data_dir
Environment="JAVA_OPTS=-Xms256m -Xmx512m -Djetty.http.host=127.0.0.1"
WorkingDirectory=/opt/geoserver
ExecStart=/usr/bin/java $JAVA_OPTS -DGEOSERVER_DATA_DIR=${GEOSERVER_DATA_DIR} -jar /opt/geoserver/start.jar
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now geoserver.service
journalctl -u geoserver.service -f

Two details that cost us time:

  • Environment="JAVA_OPTS=..." must be quoted. Unquoted, systemd treats everything after the first space as a separate, invalid assignment and silently drops it.
  • Inside the ExecStart line, write ${GEOSERVER_DATA_DIR} with braces. Without them the variable is not expanded, and GeoServer logs a misleading error on every request.

3.3 Keep the admin interface private, and change the password

The unit above binds Jetty to 127.0.0.1 only, so GeoServer is not reachable from the network. Reach the admin page through an SSH tunnel from your other computer:

ssh -L 8080:localhost:8080 ubuntu@<your-pi>
# then open http://localhost:8080/geoserver/web/ on your computer

Before anything else, change the default admin password (the default is admin / geoserver). Do this before exposing the server in any way.

3.4 Adjustments for 1 GB

The reference setup used -Xms512m -Xmx2048m on the 4 GB board. We reduced the heap to -Xms256m -Xmx512m on that same board, as a rehearsal for the 1 GB board (the unit file above uses these smaller values). What we saw:

  • With sustained load, the smaller heap was only about 10% slower for a heavy request.
  • On the first request after starting GeoServer, the small heap sometimes stalled for 12 to 30 seconds. It happened once per JVM start, for the first request that produced GML (WFS's default XML format), even a small one. GeoJSON output and WMS did not show it. It was not garbage collection. The cost appears to be first-time class loading and reflection set-up.
  • Practical advice: after a restart, send one throwaway GetFeature request and wait for it, before you begin any timing.

Things we have not measured, and that are worth your attention:

  • Total memory. The JVM's real memory use is larger than -Xmx. On the 4 GB board with a 2 GB heap cap, the process sat near 1 GB. Whether a 512 MB heap plus the operating system fits comfortably in 1 GB is the central question. Watch free -h and systemctl show geoserver.service -p MemoryCurrent.
  • A hint from a 1 GB limit on a bigger board. Our colleague ran GeoServer in a container capped at 1 GB on the Pi 4B. It used about 450 MB when idle and 450 to 570 MB under a four-worker load, and was never killed for running out of memory. The data was small (5,000 points), so this shows that GeoServer can start within 1 GB, not that it copes with heavy use.
  • Swap. Our Pi 4B ran with no swap. On a 1 GB board you may want some, but swap on an SD card is slow and wears the card.
  • PostGIS. It runs as a second service next to GeoServer and takes memory too. You may prefer to start with a read-only layer (see 3.5) before adding it.

3.5 Data: choose the storage format on purpose

BackendReadsConcurrent WFS-T writes (Pi 4B)
GeoPackageFineFailures grew with concurrency: 0% at 1 writer, 25% at 4, 45% at 8, 75% at 16
PostGISFine0 errors at every level tested, up to 16 writers

GeoPackage is a single SQLite file, and SQLite allows only one writer at a time, so this is a property of the format and not of the Pi. For a read-only service, GeoPackage is the simpler choice. For editing by several people at once, use PostGIS. If you must use GeoPackage, keep to one writer.

3.6 Three cheap improvements

These were measured on the Pi 4B. Try them on the Pi 3 and tell us whether the effect is the same.

  1. Ask for GeoJSON instead of GML when you request many features. Add outputFormat=application/json to a WFS GetFeature request. A full dump of 8,975 features was 2.3 to 2.5 times faster, with zero errors either way. The default GML output is the main cost.
  2. Set the CPU governor to performance. Ubuntu on the Pi defaults to ondemand. Switching raised WMS map-rendering throughput by 30 to 50%. 
    for g in /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor; do
  echo performance | sudo tee "$g"
done
    This resets on reboot. To make it permanent, put the same loop in a systemd oneshot unit that runs at boot (with RemainAfterExit=yes). Keep an eye on temperature (/sys/class/thermal/thermal_zone0/temp, in thousandths of a degree). Our Pi 4B stayed between 64 and 69 °C under light load.
  3. Do not bother with paging. Splitting a big dump into startIndex/count pages made sequential fetching about 1.9 times slower and did not help when done in parallel.

Also tried and not worth pursuing on our setup: class-data sharing (AppCDS) for the cold-start stall, the Marlin renderer, PostgreSQL shared_buffers/work_mem tuning, and the JAI/ImageIO native acceleration (no aarch64 build exists).

3.7 What the Pi 4B managed, for reference

  • WFS-T edits on PostGIS: zero failures in sequential and concurrent tests, including 1,200 insert-and-delete cycles over two hours.
  • Long run: a mixed read/write soak test of about 30 hours produced no server-side errors. Memory grew by about 130 MB, mostly early on, then levelled off. (Three read iterations failed, traced to the tester's own SSH tunnel dying, not to the Pi.)
  • The one workload that genuinely maxes it out: a single request for the entire unfiltered dataset. Throughput stayed near 0.7 requests per second no matter how many clients asked, because the work is limited by a single CPU core. Filtered requests, by contrast, ran at roughly 25 to 31 per second once several clients were asking (about 12 per second for a single client). If a client only needs a small area or a few attributes, ask for exactly that.

These numbers are from a Pi 4B with 4 GB and a 4-core CPU at higher clock speeds than a Pi 3. Do not expect to reproduce them; the comparison is what we are after.

4. MapServer setup

A colleague set up MapServer on a Pi 4B (4 GB) of the same kind, in a container based on Debian trixie-slim, with Apache 2, mod_fcgid, and the distribution's own MapServer packages (version 8.4.0). No source build was needed. On a Pi 3 you can try the same packages directly on Ubuntu Server. We expect the package names to be the same or very close, but the version will probably differ from 8.4.0, so check yours with mapserv -v.

4.1 Install

sudo apt install -y apache2 libapache2-mod-fcgid cgi-mapserver mapserver-bin
sudo a2enmod fcgid

MapServer's small footprint is the reason to try it on a Pi 3. We expect it to fit comfortably. We have not measured that.

4.2 The step everyone misses: MS_MAP_PATTERN

Since MapServer 8, you must explicitly allow which mapfiles may be loaded through the map= URL parameter. Without that permission, every request fails with:

msLoadConfig(): Unable to access file.

The error message does not say what is missing. The fix has two parts, and forgetting the second is easy:

  1. Create a global MapServer configuration file that contains an MS_MAP_PATTERN (a regular expression matching the paths of your mapfiles).
  2. Make sure the web server passes the environment variable that points to that file (MAPSERVER_CONFIG_FILE) through to the CGI/FastCGI process. Apache does not do this by default.

The sketch below shows the idea. It is adapted from the MapServer documentation, not copied from our working configuration, so check paths and directive names against your installation.

# /etc/mapserver.conf
CONFIG
  ENV
    MS_MAP_PATTERN "^/srv/mapfiles/[A-Za-z0-9_]+\.map$"
  END
END
# in your Apache site configuration (mod_fcgid)
FcgidInitialEnv MAPSERVER_CONFIG_FILE /etc/mapserver.conf

Then request a map with map=/srv/mapfiles/yourfile.map in the URL. If you still see the same error, first confirm that the environment variable really reaches the process.

4.3 Run it under FastCGI, not plain CGI

This is the single most important performance decision. Under plain CGI, the web server starts a new MapServer process for every request. Under FastCGI, a pool of MapServer processes stays alive and is reused. In our test the same MapServer was slower than GeoServer under CGI, then clearly faster once switched to FastCGI:

Setup (Pi 4B, WMS GetMap)Throughput
MapServer, plain CGI5.1 to 5.5 req/s
GeoServer7.6 to 13.6 req/s (13.1 to 13.6 in the repeat runs)
MapServer, FastCGI16.9 to 22.5 req/s (three repeat runs)

The lesson: MapServer's light weight is only visible when it is not being restarted for every request. Choosing how to deploy a server can matter as much as choosing which server to run.

With Apache and mod_fcgid, this means the URL points at the FastCGI form of the program rather than the plain CGI one. The exact wiring depends on your Apache layout; we will add our working configuration here once it has been reviewed.

  • How many FastCGI processes to allow. Each one holds memory, and a Pi 3 has four slow cores.
  • Whether the Pi 3 shows the same CGI-versus-FastCGI reversal.

5. Benchmark procedure

The point of a benchmark is to let you compare two servers, or two settings, fairly. Use the same data, the same request, and the same procedure every time.

5.1 The recipe

  1. Same data on both servers. We generated 5,000 random points as a Shapefile and registered the identical dataset in GeoServer and in MapServer.
  2. One request type. A WMS GetMap request, identical every time (same bounding box, size, and format).
  3. Warm up first. Send one or two requests and wait for them. The first request after starting a server is not representative (see the cold-start stall in section 3.4).
  4. Four parallel workers, 20 requests each, 80 in total.
  5. Measure the wall-clock time from when the workers start to when the last one finishes.
  6. Throughput = 80 ÷ wall-clock seconds.
  7. Repeat at least three times and report the range, not a single number. Run-to-run variation on a small board is large.

Why wall-clock time? Adding up each request's own duration overstates the total when requests overlap. Dividing the number of requests by the real elapsed time gives what a user would actually experience.

5.2 A small script

This needs only Python 3, which Ubuntu already includes. Save it as bench.py, and fill in your own URL.

#!/usr/bin/env python3
"""4 workers x 20 requests; prints wall-clock throughput."""
import sys, time, urllib.request
from concurrent.futures import ThreadPoolExecutor

URL = sys.argv[1]          # the full GetMap URL, in quotes
WORKERS, PER_WORKER = 4, 20

def worker(_):
    errors = 0
    for _ in range(PER_WORKER):
        try:
            with urllib.request.urlopen(URL, timeout=60) as r:
                r.read()
        except Exception:
            errors += 1
    return errors

urllib.request.urlopen(URL, timeout=120).read()   # warm-up, not timed

t0 = time.monotonic()
with ThreadPoolExecutor(max_workers=WORKERS) as pool:
    errors = sum(pool.map(worker, range(WORKERS)))
wall = time.monotonic() - t0

total = WORKERS * PER_WORKER
print(f"requests={total} errors={errors} wall_s={wall:.2f} "
      f"throughput={total / wall:.1f} req/s")

Example call (adjust host, layer, and bounding box). The & characters need the quotes:

python3 bench.py "http://localhost:8080/geoserver/wms?service=WMS&version=1.1.1&request=GetMap&layers=yourworkspace:yourlayer&styles=&bbox=-180,-90,180,90&width=768&height=768&srs=EPSG:4326&format=image/png"

For MapServer, use its own URL with map=...&service=WMS&request=GetMap....

5.3 Run it from the right place

  • Run the script on the Pi itself when you want the server's speed, without the network in the way. Note that the script then competes with the server for the same four cores.
  • Run it from another computer when you want to include the network. Say which one you did.
  • If you use an SSH tunnel for a long run, remember that a laptop that goes to sleep will kill the tunnel. In our 30-hour run, this was the only failure.

5.4 Record the machine state alongside the numbers

free -h
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
awk '{ printf "%.1f C\n", $1/1000 }' /sys/class/thermal/thermal_zone0/temp
uptime

A hot board slows itself down (thermal throttling), and the governor changes results by tens of percent, so numbers without these are hard to interpret later.

6. Known pitfalls

Every item here cost somebody real time. Skim the list before you start.

Choosing and deploying

  • CGI versus FastCGI can reverse the result. MapServer under CGI lost to GeoServer; under FastCGI it won. Do not judge MapServer until it is running under FastCGI (see 4.3).
  • Tomcat and GeoServer must be from the same servlet generation. If you deploy GeoServer as a .war in Tomcat, a GeoServer built for javax.servlet (Tomcat 9) will not start on Tomcat 11 (jakarta.servlet). The symptom is a NoClassDefFoundError. Check which servlet generation your GeoServer version needs before you pick a Tomcat image. The bundled-Jetty binary in section 3 avoids the question.
  • Docker is not automatically the easy path on ARM. No official GeoServer arm64 image at the time of writing; the workable route is an official Tomcat image plus the .war (see 3.1).

Configuration traps

  • Getting the Pi onto the network in the first place has its own traps: both cable and Wi-Fi in network-config, dhcp4: true on Wi-Fi, and cloud-init running only once per card (see 2.2).
  • MapServer 8 needs MS_MAP_PATTERN and a web server that passes it on. The error message (msLoadConfig(): Unable to access file.) does not point at the cause (see 4.2).
  • systemd quoting: quote Environment="JAVA_OPTS=..." and use ${VAR} with braces inside ExecStart (see 3.2).
  • GeoServer's REST shortcut for registering a Shapefile (the external.shp form) returned an unexplained error for us. The longer, standard XML-POST way to create a datastore worked.
  • Change the default GeoServer admin password before doing anything else, and keep the admin interface off the open network (see 3.3).

Performance surprises

  • The first GML request after a restart can stall for 12 to 30 seconds on a small heap. Warm up before you measure (see 3.4).
  • Asking for the whole dataset at once is the expensive operation. Filter, or request a small area (see 3.7).
  • GeoJSON is much cheaper than GML for large results (see 3.6).
  • The CPU governor matters, and it resets on reboot (see 3.6).

Data and concurrency

  • GeoPackage is unreliable under concurrent writes; PostGIS is not (see 3.5). This is the format, not the Pi.
  • PostGIS accumulates dead rows between automatic cleanups when you edit and delete a lot. In our two-hour test it was about 14% of live rows, harmless on a small table. On a large table with heavy editing, watch disk space.

Measuring

  • Do not compare numbers from different hardware or different data and call it a verdict. Our Pi 4B figures and our colleague's container figures used different data and different setups. Compare only what you ran under the same conditions.
  • Check a suspicious result in two ways before believing it. One of us briefly concluded that container memory limits were switched off, because we had looked in the wrong place for the setting (the older cgroup version instead of the current one). The limit was working all along.
  • The 1 GB experiment on a 4 GB board did not settle the question. Limiting a container to 1 GB on the Pi 4B did not squeeze GeoServer, because it never used more than about 600 MB with that small dataset. A real Pi 3, with larger data and more load, is the test that counts.
  • A long test from a sleeping laptop will be interrupted. Run long tests from a machine that stays awake.
